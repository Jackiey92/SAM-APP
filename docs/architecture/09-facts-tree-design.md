# 公司事实树（Facts Tree）设计 v1.2

> 状态：设计稿（评审修订版）　架构：饭团　日期：2026-10-14
> 上游：`docs/architecture/06-2b-l1-l0-design.md`（文件名沿用历史，其中的层级代号在本设计中已改为语义命名）
> v1.1 修订：①弃用 taxonomy 命名改树语言；②每个树枝自带 L1+L0；③原子卡不进记忆层、归文档库；④全部产物不加前置下划线；⑤路径协议用 sam://。
> v1.2 新增：**可插拔事实模板（§10）**——事实模板做成模板包，在**注册公司（建档）时连同公司名一起选定并绑定**；插拔只发生在该公司记忆层**为空**时，一旦写入事实模板即锁定，不做后期更换与搬家迁移。路径与内部代号全部语义化（sam://facts、parsed/）。

---

## 0. 为什么做这一版

M5-B 真机暴露：原子键值卡数字核验稳，但核心技术/工艺/模式等成段描述装不进（"纳米级涂膜技术"在事实与简报层都检索不到）；指标命名发散、公司间不可比、漏没漏不可见。

方案：预设一棵**从公司视角、通用**的事实树，事实装进固定叶子，叶子是可读 Markdown；文件驱动、只由文件管理员一个工种完成。叶子以叙事为主，文末保留可逐字核验的数字底座——拿可读性，不丢防假数。

## 1. 术语与分层（v1.1 重定）

### 1.1 一棵树的三个部件

| 部件 | 名称 | 含义 |
|---|---|---|
| 整棵树 | **facts tree** | 一家公司事实记忆层的全部事实 |
| 树枝 | **facts trunk** | 固定 10 个业务分支（即现有 10 个模块），代码称 module，配置文件称「树枝目录」 |
| 叶子 | **fact leaf** | 树枝下最末一层，一个叶子 = 一篇主题 Markdown，不再下钻 |

> 命名弃用 "taxonomy"。现有代码 `app/module_taxonomy.py` 在落地时改名为 `app/module_tree.py`（`validated_module`→`validated_trunk` 等同步改），后端逻辑不变；可编辑的配置文件叫「树枝目录 / 事实树模板」，不再叫 taxonomy 清单。

### 1.2 两层存储边界（关键修正）

```
【文档库】（原件层，不是记忆层）
  sam://library/<company>/
    original/<sha256>          原件二进制（不可变）
    parsed/<sha256>.md         解析净稿（带坐标切块，审核修订后的干净文本）
    facts.sqlite               原子事实正本（逐字核验、可计算的最小事实）
    review-log/                解析审核修订的 diff 留痕

【模板仓库】系统级图纸，与具体公司无关（详见 §10）
  sam://templates/<pack-id>-<version>/pack.yaml、leaves/*.md

【记忆层 · 事实树】（由文档库提炼，只放对人可读的成稿）
  sam://facts/<company>/
    tree.meta                  建档信息：公司名 + 绑定的模板包 id/version（注册时定）
    tree-brief.md              L1 整棵树·公司简报（跨树枝聚合）
    tree-guide.md              L0 整棵树·公司导览（常驻经理上下文）
    01-企业基本信息/
        trunk-brief.md         L1 树枝简报（本树枝叶子聚合）
        trunk-guide.md         L0 树枝导览（本树枝入口）
        leaves/L-info-03-公司发展历程.md   L2 事实叶子（有事实才建）…
    …
    待办与冲突/                  数字/表述打架、裸数字、越界候选（系统枝）
    待归类/                      判不准归属的叶子（系统枝）
```

- **原子事实卡不进记忆层**：它是 SQLite 正本里的结构化记录（文档库），继续承担"逐字命中 + 可计算"，但**不再投影成一份 md 放进事实记忆层**。
- 记忆层最小单位是**叶子（L2）**。叶子「数据明细」里用 `fact_id` **回链**文档库原子记录，需要核验/算数时去文档库取，记忆层不复制一份。
- 解析净稿与原件同属文档库，是叶子和原子卡的共同取证来源。

### 1.3 事实树三层命名定稿

| 层 | 名字 | 粒度 | 产物 |
|---|---|---|---|
| L2 | **facts leaf** | 一个方面一篇 | 每树枝 `leaves/*.md` |
| L1 | **brief 简报** | 树枝 / 整棵树 | `trunk-brief.md` / `tree-brief.md` |
| L0 | **guide 导览** | 树枝 / 整棵树 | `trunk-guide.md` / `tree-guide.md` |

聚合方向：叶子 → 树枝 brief/guide → 树 brief/guide。**树枝先各自形成自己的 L1+L0，整棵树再形成一份 L1+L0**；上层只能从下层聚合，不回读旧稿、不引入下层没有的数字。

> 命名规则：所有产物**一律不加前置下划线**（`_brief/_guide/_待办…` 全部废除）。

## 2. 十条树枝（对齐现有模块，code 不变）

| code | 树枝 | 装什么（边界） |
|---|---|---|
| `info` | 01-企业基本信息 | 主体登记资格、沿革、股权与控制、子公司、组织架构 |
| `bizov` | 02-业务概览 | 商业模式、产品、技术、研发、知识产权（**事**） |
| `hr` | 03-人员管理 | 团队、员工、激励——所有"**人**" |
| `prod` | 04-生产 | 生产模式、工艺、产能、设备、厂房、成本 |
| `purch` | 05-采购 | 供应、供应商、采购账期、采购类关联交易 |
| `sales` | 06-销售 | 收入、定价、渠道、客户、订单、售后 |
| `mkt` | 07-市场 | 行业、产业链、市场规模、竞争、替代品（外部环境） |
| `fin` | 08-财务 | 三表核心数据、财务预测 |
| `fund` | 09-融资 | 股权/债权融资、对赌、本轮方案、上市规划 |
| `legal` | 10-法务合规 | 资质牌照、诉讼仲裁、环保安全、税务补贴、重大风险 |

**归属总原则（公司视角 + 通用）**：按"这是谁的属性/哪件事"归，不按尽调提问顺序归。

- **人 → hr**："核心技术人员"的资历、持股、稳定性是人的属性，归 03。
- **技术/事 → bizov**：技术本身、研发投入（钱）、专利清单是业务能力，归 02。
- 公司与外部：上游→purch，下游→sales，行业与对手→mkt。
- **info 与 legal 的分界（防工商档案两头存）**：
  - **登记事实与结构**归 info：营业执照信息、注册资本、经营范围、章程、股东及变更历史——"公司是什么、由谁构成"。
  - **合规状态与争议**归 legal：资质牌照及其效力、行政处罚、诉讼仲裁、税务环保违规、风险事项——"公司有没有出事/合不合规"。
  - 例：营业执照本身、注册资本→info-01；因经营范围或资质引发的处罚、资质到期风险→legal。同一事实只存一处，另一处需要时用叶子名交叉引用，不复制。
- 通用性：叶子名不绑定行业（不出现"涂布/晶圆"）；非制造公司不实例化产能叶子即可，不删模板、不标缺口。
- 10 树枝是固定主干；具体有哪些叶子以**模板包**形式存在（见 §10），注册公司时绑定；后端代码无任何归类 if/正则/关键词（铁律）。

## 3. 叶子全集（通用模板，98 叶）

叶子编码 `L-<MODULE>-<NN>`，稳定、跨公司可比。

**「形态」列含义**：
- **n = 叙述型（narrative）**：以成段文章为主体，讲清来龙去脉（技术、模式、工艺、历程、判断），数字就地写进句子；文末数据明细可省或很短。
- **s = 数据型（structured）**：以结构化数字表为主体（财务、股权、员工、产能、客户占比），正文只需一两句概述，重在「数据明细」整齐可算。

## 4. 叶子文档契约

### 4.1 路径与命名（协议用 sam://，无下划线）
```
叶子：sam://facts/<company>/<NN-树枝名>/leaves/L-<module>-<NN>-<叶子名>.md
例：  sam://facts/<company>/02-业务概览/leaves/L-bizov-07-核心技术与关键难点.md
树枝：…/<NN-树枝名>/trunk-brief.md、trunk-guide.md
整树：…/tree-brief.md、tree-guide.md
冲突：…/待办与冲突/conflict-<module>-<metric>-<jobid>.md
```

### 4.4 证据颗粒度（最细）
- 每个自然段段末必有脚注，无来源句不允许存在。
- 每张表逐行在"来源"列标脚注；一行多源就多列。
- 脚注定义为 `原件名 → 坐标`，坐标由解析块回填，员工不得自编。
- 多文件同指标：正文按时间线融合，数据明细按期间多行、各自带源。

### 4.5 铁律
- **不标缺口**：麻袋只装事实，没有就不实例化、前台不显示，不写"缺失/待补"。
- **冲突不入叶**：确定叶子只放核验通过值，打架转「待办与冲突」。
- **数字不漂**：正文每个数字能在数据明细→文档库原子记录逐字回查；数字护栏对叶子同样生效。
- 叶子只从文档库解析净稿 + 原子记录生成/更新，**不回读旧叶子改写**。

## 5. 单员工、双技能

只有一个员工 **文件管理员 `document_manager`**（不新增工种），按工序挂技能：

| 技能 | 工序 | 读什么 | 产出 |
|---|---|---|---|
| 技能A：解析审核与修订（`file-processor` 演进） | 入库前 | 原件 + 解析切块 | 放行 / 调原件局部修订 / 返工重转 / 转人 |
| 技能B：分类与事实整理（classifier+finance-fact+新增 `fact-leaf`） | 入库后 | **只读技能A 放行的解析净稿** | 判树枝、原子记录入 facts.sqlite、写/更新叶子 |

以入库门分界：**A 管"原件→解析净稿（文档库）"，B 管"解析净稿→原子记录+事实树（记忆层）"**；B 不开放原件通道。

## 6. 解析审核与修订（技能 A 扩权）

现状（`app/document_quality/gate.py`）：已能取原件快照（`sam://original/<hash>`）、列带坐标问题、要求解析器重转（≤3 次）、否则转人。新增第三条路径：**调原件局部 → 就地修订解析切块**。

- 触发：重转也修不好的结构混乱（复杂合并表头、跨页表、扫描 OCR 错、PDF 串行）。
- 可调：仅本区间块的原件局部（表格矩阵/原版面/OCR 图），坐标后端签发，不能翻整本、不能自编坐标。
- 动作：在切块结构上原地修订，改完后端重钉坐标，再走质检放行；修订 diff 入文档库 review-log。

**三条红线：**
1. 只还原不改意：数字、年份、专名、原文措辞一字不改，原件没有的不补。
2. 全程留痕可回滚：改前/改后 diff、依据页码、runId 可逐块对回原件。
3. 坐标不漂移：原地改、重钉坐标，禁止整篇打散（**头号验收项**，否则逐字命中门卫失效）。

## 7. 冲突枝「待办与冲突」

- 触发：同指标两个候选核验不为同值（如研发人员占比正文 14.86% vs 表三年 12.77/13.33/19.51%）。
- 处置：两候选都不进确定叶子，各带坐标在 `待办与冲突/` 立 `conflict-*.md`，只摆候选值/出处/来源/待谁裁。
- 裁决（范范/经理）后：胜出值写入叶子并追加编辑历史；冲突件 `status: archived`、前台隐藏、留档。
- 裸数字、越界、空壳候选按现有 unresolved/hand-off 进此枝。

## 8. 文件驱动处理流程（非叶子遍历）

1. **解析器**：二进制→切块解析净稿，发坐标，原件入文档库。
2. **技能A**：逐块审保真，差则修订/返工，放行的解析净稿入文档库。
3. **技能B**：
   - 判文件涉及哪几个树枝（可多挂），判不准进「待归类」；
   - 从解析净稿取证 → 原子记录入 facts.sqlite → 定位/新建叶子并更新；
   - 段段脚注、表逐行来源、多源全列；撞冲突转「待办与冲突」。
4. **树枝聚合**：受影响叶子更新后，重建该树枝 `trunk-brief.md`/`trunk-guide.md`；再按需重建 `tree-brief.md`/`tree-guide.md`（只从下层聚合）。
5. **成本闸门**：不做 98 叶×全库扫描，按文件命中的树枝/叶子增量重算，未命中叶子 updated_at 不变；叶子清单当覆盖检查单，但没装的叶子静默、不报警。

## 9. 前台显隐

- 废除模块级整模块隐藏（现 prod/purch/sales/fin/fund 的 hidden 作废）。
- **叶子级显隐：有 active 叶子才上前台，空叶子只在模板仓库。**
- 树枝下至少一个可见叶子时，树枝导航才出现；可见叶子数/更新时间可作角标。
- 冲突件、归档件、待归类件不进事实前台，只在待办中心对有权限者可见。

## 10. 可插拔事实模板（注册时绑定）

### 10.1 一句话原则

**模板是公司的"出厂图纸"，在建公司那一刻随公司名一起选定并绑定；图纸可以插拔，但只在仓库还是空的时候。一旦往里写了事实，图纸锁定，不支持后期更换。**

这样设计的理由：叶子编码（L-bizov-07 这类）是事实的稳定坐标，中途换图纸会让已经写好的事实对不上号、产生漂移；所以"可插拔"严格限定在开仓那一刻，之后图纸只随版本向后兼容地长（加叶子），不换、不重排。

### 10.2 两个层次：模板包（图纸） vs 公司事实（货物）

```
【模板仓库】系统级、与具体公司无关，可有多套，随系统版本发布
  sam://templates/
    general-v1/                 通用综合模板包（§3 的 98 叶）
      pack.yaml                 包元信息：id/version/10 树枝/叶子清单(编码·名称·形态·要点)
      leaves/L-bizov-07.md      每片叶子的空白骨架（四段式 + frontmatter 占位）
    semiconductor-equip-v1/     垂类包：半导体设备
    new-materials-v1/           垂类包：新材料
    …

【公司事实树】某一家公司，注册时绑定一个模板包（通用包 + 可选垂类包）
  sam://facts/<company>/
    tree.meta                  建档信息：公司名、绑定的模板包 id+version、绑定时间
    tree-brief.md / tree-guide.md
    01-企业基本信息/ …
```

- **模板包**是纯配置（pack.yaml + 叶子骨架），不含任何公司事实；加一套垂类=在模板仓库加一个包，不改后端代码、不加任何关键词/枚举到代码里（铁律不变，模板是数据不是程序）。
- **公司事实树**在建档时引用某个模板包版本；叶子文件在"第一次真有事实要写"时，才由技能 B 按对应骨架创建——**注册时不预生成 98 个空文件**（呼应"不标缺口、有内容才显示"）。

### 10.3 插拔规则（只有一个窗口：空仓）

| 公司记忆层状态 | 能否换/选模板 |
|---|---|
| 尚未建档 | 建档时任选一套模板包（通用 / 通用+某垂类） |
| 已建档、但记忆层为空（无任何叶子/原子事实） | **可以换绑**另一套模板包，仅改 tree.meta 绑定，无事实可搬，零成本 |
| 已写入任意事实（有 active 叶子或原子记录） | **锁定，不可更换模板包**；只允许该包向后兼容升级（见 10.5） |

- 换绑是"换张图纸"，不是搬货：空仓没有货，所以不存在数据迁移。
- 若一家公司确实要彻底换图纸，正路是**另开一家新公司建档**（或重置为空再选），而不是在有事实的树上热替换。

### 10.4 绑定关系记在哪

- `sam://facts/<company>/tree.meta` 记录：公司名、`template_pack: general-v1 + semiconductor-equip-v1`、各自版本号、绑定时间、操作责任。
- 每片叶子 frontmatter 的 `leaf_code` 来自其绑定包；因为绑定后锁定，编码终身稳定。
- 通用包与垂类包是"底座 + 挂接"：垂类包**只能在 10 个既有树枝下新增/细化叶子**，不动 10 树枝 code、不改通用包已有叶子编码，保证所有公司主干一致、可横向对齐。

### 10.5 模板包自身的版本演进（区别于"换模板"）

- 模板包可以发新版本（如 general-v1.1 增补几片叶子），这是**图纸升级**，不是给某家公司换模板。
- 已建公司是否跟升到新版本：只允许**向后兼容的增量**（新增叶子），不删除/不重排/不改编码；存量叶子不受影响，新增叶子对该公司同样"有内容才实例化"。
- 是否跟升、何时跟升，属于建档配置决策（经理/范范），后端只做"绑定版本存在性 + 兼容性（只增不改编码）"的结构校验，不做业务判断。

### 10.6 与后端铁律的关系

模板包是给员工（技能 B）读的"装填指引"：员工看包内叶子清单判断事实装进哪片叶子。后端**不解析模板内容做归类**，只负责模板仓库存取、建档绑定、空仓换绑门、版本兼容校验；判类和选叶子始终是员工语义决策。

## 11. 后端职责（只护栏，无业务规则）

- 文档库：原件/解析净稿/facts.sqlite/review-log 的存储、哈希、URI、并发锁。
- 模板仓库：模板包（pack.yaml+叶子骨架）的存取、版本管理；不解析其内容做归类。
- 建档与绑定：注册公司时绑定模板包并写 tree.meta；**空仓换绑门**——记忆层非空时拒绝换绑；模板升级只校验"只增叶子、不改既有编码"的向后兼容。
- 记忆层：树枝/叶子/简报/导览的 mkdir、幂等重建、sam:// URI 三层契约、传输超时。
- 受控"取原件局部"工具：区间校验、坐标签发、diff 留痕、坐标重钉、回滚。
- 数字护栏：叶子每个数字可回查原子记录，查不到拒收，不替员工补来源或改数。
- 叶子显隐按是否存在 active 实例计算；frontmatter/status/编辑历史结构校验；写入 vectors_only。
- 重命名落地：module_taxonomy→module_tree 等，纯改名+引用更新，行为不变。
- **禁止**任何识别公司/年份/数字/行业/归类的正则、关键词、枚举、映射、写死公式；判类/归属/选叶子全是员工语义决策。
